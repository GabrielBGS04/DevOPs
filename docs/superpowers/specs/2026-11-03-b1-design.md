## Interfaces e comportamento

### Core e ranking

Preservar `/api/alunos`, `/api/alunos/{id}`, `/api/cursos` e `/api/alunos/{id}/concluir-curso`. Acrescentar `GET /api/ranking` com itens contendo `alunoId`, `nome`, `cursosConcluidos` e `pontos`. Para o experimento, cada entrada distinta no histórico vale 100 pontos; ordenar por pontos decrescentes e depois por ID crescente. Não criar moedas apenas para reproduzir a fórmula do ZIP.

O ranking usa uma projeção de leitura, sem permitir acesso externo às classes de persistência internas dos módulos. A contagem pelo histórico atual é uma adaptação didática, não uma prova de capacidade para 100 mil usuários.

### Serviço de IA

O Core oferecerá `GET /api/alunos/{id}/recomendacoes` e `POST /api/assistente`, com pergunta no campo `pergunta`. O serviço Python receberá o catálogo/histórico necessário, sem acessar diretamente o banco do Core. Recomendação: cursos ainda ausentes do histórico, ordenados por ID, no máximo três. Assistente: busca textual simples em conteúdo local, devolvendo a resposta demonstrativa e a fonte; quando não houver correspondência, informar que o conteúdo local não respondeu à pergunta.

Usar um único serviço Python para essas duas rotas, com código separado por responsabilidade. Timeout total da chamada HTTP: dois segundos, sem retentativa na requisição do usuário. Falha, timeout ou resposta inválida da IA resultam em HTTP 200 degradado, com `disponivel=false`: lista vazia para recomendações e mensagem de indisponibilidade para o assistente. Aluno inexistente mantém a resposta 404 do Core. Identificar a solução como demonstração de integração; ela não treina ML nem implementa RAG/LLM completo.

### Notificações

Registrar conclusão e bônus sincronicamente. Gravar o evento de notificação na mesma transação do estado do Core. Um worker separado da thread HTTP entregará eventos pendentes ao receptor Python simulado. Usar identificador estável do evento, timeout de dois segundos por tentativa e nova tentativa a cada cinco segundos. Marcar como entregue somente após confirmação do receptor. A entrega é pelo menos uma vez; o receptor deduplica o identificador em armazenamento persistente local, SQLite em volume do serviço de integrações.

Para a demonstração síncrona, usar script de laboratório que chama o receptor e registra falha HTTP; não colocar essa dependência no fluxo essencial de produção. Mostrar que ela impede a confirmação da notificação, enquanto a alternativa assíncrona mantém conclusão e bônus disponíveis. Não afirmar atomicidade distribuída entre Core e receptor.

### IoT

Usar o tópico `b1/atividades`, MQTT QoS 1, sessão persistente e armazenamento do Mosquitto em volume. O gateway no processo Python de integrações encaminhará o evento por HTTP para `POST /api/iot/eventos`.

O contrato terá `eventId`, `tipo`, `dispositivoId`, `alunoId`, `cursoId` e `nota`. Tipos: `PRESENCA`, `INICIO` e `CONCLUSAO`. Nota será obrigatória somente para conclusão. Presença/início serão registrados; conclusão chamará o caso de uso existente. Gravar o identificador recebido e os efeitos de negócio na mesma transação. Repetir o mesmo `eventId` retorna sucesso sem aplicar novamente a recompensa. Evento inválido retorna 400 sem efeitos.

O gateway confirma o recebimento MQTT depois de o Core aceitar o evento. Ao falhar o HTTP, preservar o evento para nova tentativa; o teste de reconexão abrangerá essa janela. O laboratório não altera a política do endpoint legado para conclusões manuais repetidas com requisições distintas: a deduplicação será por identificador do evento IoT.

### Operação

Executáveis previstos: `core`, `ia` e `integracoes`. Acrescentar `mqtt`, `jenkins`, `prometheus` e `grafana` no Compose com perfis para subir apenas o necessário a cada desafio. O gateway e o receptor de notificações compartilham o processo de integrações para reduzir a operação do laboratório.

Cada pipeline executa testes, constrói a imagem e atualiza somente o componente correspondente no ambiente local. O agente Jenkins precisa de acesso explícito a um engine de containers; documentar a configuração usada. Sem esse agente, o pipeline permanece pendente de demonstração. Não substituir a prova no Jenkins por um print de testes locais.

O Core expõe health e métricas Prometheus. Métricas: duração/erros HTTP, falhas de chamadas à IA e notificações pendentes. Não usar IDs de alunos ou eventos como labels de métricas. Registrar esses IDs nos logs para correlacionar os experimentos.
